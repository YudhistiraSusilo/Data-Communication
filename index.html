1 Prinsip Aplikasi Jaringan

Aplikasi jaringan hidup di end system (ujung jaringan) — bukan di dalam jaringan inti. Di sinilah letak "kecerdasan" jaringan diletakkan.

Berbagai aplikasi jaringan yang kita pakai sehari-hari: media sosial, Web, pesan teks, e-mail, game multiplayer, streaming video (YouTube, Netflix), P2P file sharing, voice-over-IP (VoIP), video conference (Zoom), mesin pencari, remote login, dan lainnya.

Kunci utama: aplikasi jaringan ditulis sebagai program yang berjalan di end system (PC, ponsel, server web). Kita tidak perlu menulis perangkat lunak untuk perangkat network core (router, switch) — perangkat itu hanya meneruskan data. Inilah yang membuat pengembangan aplikasi jaringan cepat: cukup buat program di kedua ujung.

Dua arsitektur aplikasi

Client–Server

  • Server: host yang selalu menyala (always-on), alamat IP permanen, sering berada di datacenter agar mudah ditingkatkan skalanya.
  • Client: menghubungi server, boleh terhubung tidak terus-menerus (intermittent), bisa punya IP dinamis, dan tidak berkomunikasi langsung dengan client lain.
  • Contoh: HTTP, IMAP, FTP.

Peer-to-Peer (P2P)

  • Tidak ada server always-on; host arbitrari saling berkomunikasi langsung.
  • Setiap peer meminta layanan sekaligus menyediakan layanan kepada peer lain.
  • Self-scalability: peer baru membawa kapasitas layanan sekaligus permintaan baru.
  • Peer terhubung secara intermittent dan berganti IP → manajemen rumit.
  • Contoh: P2P file sharing (BitTorrent).
Gambar 1 — Arsitektur client–server vs peer-to-peer.
Analogi: Restoran vs Dapur bersama Client–server seperti restoran: satu dapur (server) melayani banyak pelanggan (client). Pelanggan tak berhubungan satu sama lain, semuanya "berbicara" ke dapur. Kekurangannya: kalau dapur libur, semua hampa. P2P seperti dapur bersama (potluck): setiap orang membawa makanan sekaligus makan dari yang dibawa orang lain — makin banyak orang datang, makin banyak juga makanan yang tersedia (self-scaling), tapi tidak teratur dan tidak bisa diandalkan.

Proses yang berkomunikasi

Proses = program yang sedang berjalan di dalam sebuah host. Dalam satu host, dua proses berkomunikasi lewat inter-process communication (diatur sistem operasi). Dua proses di host berbeda berkomunikasi dengan bertukar message lewat jaringan. Dalam arsitektur P2P pun tetap ada peran: client process = yang memulai komunikasi, server process = yang menunggu dihubungi.

Soket (Socket): "pintu" antara aplikasi dan transport

Proses mengirim/menerima pesan melalui soket. Soket itu seperti pintu: proses yang mengirim "mendorong" pesan keluar pintu, lalu infrastruktur transport di sisi lain pintu yang mengantarnya sampai ke soket proses penerima. Ada dua soket — satu di tiap sisi. Perhatikan pembagian kendali: aplikasi (pembuat aplikasi) mengendalikan yang di dalam pintu; sistem operasi mengendalikan yang di luar pintu (transport ke bawah).

Gambar 2 — Soket adalah pintu antara aplikasi dan protokol transport.

Menunjuk proses: IP + port

Untuk menerima pesan, sebuah proses butuh identitas. Host punya alamat IP 32-bit yang unik. Tapi IP saja tidak cukup: pertanyaan di slide — "apakah IP host cukup untuk mengidentifikasi proses?" Jawabannya tidak, karena banyak proses bisa berjalan di host yang sama. Maka identitas proses = alamat IP + nomor port.

  • HTTP server → port 80
  • Mail server → port 25
  • Contoh: kirim pesan HTTP ke gaia.cs.umass.edu → IP 128.119.245.12, port 80

Yang didefinisikan protokol application layer

  • Jenis message yang dipertukarkan: request, response
  • Sintaks: field apa saja dalam pesan dan bagaimana field dipisahkan
  • Semantik: arti informasi dalam tiap field
  • Aturan: kapan dan bagaimana proses mengirim & merespons pesan

Protokol terbuka

Didefinisikan di RFC, semua orang bisa mengaksesnya → interoperable. Contoh: HTTP, SMTP.

Protokol proprietary

Milik satu pihak, tertutup. Contoh: protokol Zoom.

Layanan TCP

  • Transfer reliabel antar dua proses.
  • Flow control: sender tidak membanjiri receiver.
  • Congestion control: menahan sender saat jaringan padat.
  • Connection-oriented: ada setup sebelum kirim data.
  • Tidak menyediakan: timing, jaminan throughput minimum, security.

Layanan UDP

  • Transfer tidak reliabel antar dua proses (datagram).
  • Tidak menyediakan: reliability, flow control, congestion control, timing, jaminan throughput, security, ataupun connection setup.
Mengapa UDP ada? Karena tidak semua aplikasi butuh yang TCP berikan. Aplikasi yang toleran loss dan peka delay (game, VoIP, DNS) lebih suka UDP: komunikasi langsung tanpa handshake = lebih cepat, tanpa retransmisi = delay rendah, dan aplikasi mengendalikan sendiri "fitur" yang dibutuhkannya (mis. QUIC melapisi TCP-like di atas UDP).

Mengamankan TCP: TLS

Soket TCP/UDP "mentah" (vanilla) tanpa enkripsi — password yang diketik akan melintasi internet dalam teks terang (cleartext!). Solusinya TLS (Transport Layer Security):

  • Menyediakan koneksi TCP terenkripsi.
  • Integritas data + end-point authentication.
  • TLS diimplementasikan di application layer (aplikasi memakai library TLS yang memakai TCP di bawahnya).
  • Dengan TLS, cleartext yang masuk ke "soket" menjadi terenkripsi saat melintasi internet. (Detail lanjutan: Chapter 8.)
Analogi: Pintu, alamat, dan amplop Soket = pintu rumah yang anda dorong suratnya keluar; anda tidak peduli jalan apa yang dilewati tukang pos. IP + port = nomor rumah plus nama penerima di dalam rumah (alamat kota tanpa nama orang tidak cukup). TCP vs UDP = kurir yang menelpon dulu, mencatat resi, dan mengulang kalau rusak (TCP) vs melempar pos udara begitu saja tanpa konfirmasi (UDP). TLS = surat dalam amplop tersegel yang tak bisa dibaca siapa pun di tengah jalan.

2 Web dan HTTP

HTTP (HyperText Transfer Protocol) adalah protokol application layer Web: client (browser) meminta objek, server Web mengirimnya.

Konsep dasar Web

  • Sebuah web page terdiri dari objek; tiap objek bisa disimpan di server yang berbeda.
  • Objek bisa berupa file HTML, gambar JPEG, Java applet, file audio, dsb.
  • Halaman = file HTML dasar yang merujuk sejumlah objek, masing-masing dialamati URL, contoh www.someschool.edu/someDept/pic.gif → bagian host name dan path name.

Model HTTP

  • Client (browser seperti Safari/Firefox) meminta & menampilkan objek; server (mis. Apache) mengirim objek sebagai respons.
  • HTTP memakai TCP: client membuka koneksi TCP (soket) ke server port 80; server menerima; keduanya bertukar pesan HTTP; koneksi ditutup.
  • HTTP bersifat stateless: server tidak menyimpan informasi tentang permintaan client sebelumnya. Mengapa dirancang begitu? Protokol yang menjaga "state" itu rumit: state harus dipelihara, dan jika client/server crash maka pandangan keduanya tentang state bisa tak konsisten dan harus didamaikan.

Dua jenis koneksi HTTP

Non-persistent HTTP

  • Satu koneksi TCP dibuka, paling banyak satu objek dikirim, lalu koneksi ditutup.
  • Mengunduh banyak objek = butuh banyak koneksi.

Persistent HTTP (HTTP 1.1)

  • Koneksi TCP tetap terbuka setelah respons; objek berikutnya dikirim lewat koneksi yang sama.
  • RTT untuk semua objek bisa hanya satu — waktu respons terpotong separuh.
Gambar 3 — Non-persistent vs persistent HTTP: berapa RTT yang dibutuhkan.

Menghitung waktu respons (RTT)

RTT (Round-Trip Time) = waktu bagi paket kecil untuk pergi dari client ke server dan kembali.

  • Non-persistent, per objek: 2 RTT (1 RTT init koneksi TCP + 1 RTT request & awal respons) + waktu transmisi file. Rumus: Response time = 2×RTT + waktu transmisi.
  • Masalah non-persistent: butuh 2 RTT per objek + overhead OS untuk tiap koneksi TCP; browser biasanya membuka beberapa koneksi paralel untuk mengunduh objek rujukan sekaligus.
  • Persistent HTTP/1.1: server membiarkan koneksi terbuka setelah mengirim respons; client mengirim request begitu menemukan objek yang dirujuk.

Format pesan HTTP request

Pesan HTTP berbentuk ASCII (mudah dibaca manusia), berisi request line, header lines, lalu baris kosong \r\n sebagai penanda akhir header.

GET /index.html HTTP/1.1\r\n
Host: www-net.cs.umass.edu\r\n
User-Agent: Mozilla/5.0 (Macintosh; Intel Mac OS X 10.15) Firefox/80.0 \r\n
Accept: text/html,application/xhtml+xml\r\n
Accept-Language: en-us,en;q=0.5\r\n
Accept-Encoding: gzip,deflate\r\n
Connection: keep-alive\r\n
\r\n

Baris pertama = request line berisi method (GET, POST, HEAD), URL, dan versi. Format umum request: method sp URL sp version crlf diikuti header field-name: value lalu crlf dan entity body.

Cookies: menjaga state walau HTTP stateless

HTTP/GET tidak membawa "state", tetapi website dan browser memakai cookies untuk menjaga state antar transaksi. Cookies punya empat komponen:

  1. Baris header Set-Cookie dalam pesan respons HTTP.
  2. Baris header Cookie dalam pesan request HTTP berikutnya.
  3. Berkas cookie yang disimpan di host pengguna, dikelola browser.
  4. Back-end database di situs web.

Contoh: Susan pertama kali mengunjungi toko e-commerce. Saat request awal tiba, situs membuat unique ID (cookie) dan entri database untuk ID itu. Request berikutnya dari Susan menyertakan ID cookie → situs bisa "mengenali" Susan.

Gambar 4 — Alur cookie: respons menetapkan cookie, request berikutnya memakainya.

Kegunaan cookies: otorisasi, keranjang belanja, rekomendasi, state sesi (web e-mail). Cookies & privasi: situs bisa belajar banyak tentang Anda. Third-party cookies (tracking cookies) memungkinkan identitas yang sama dilacak di banyak situs — bahkan lewat link tak terlihat, tanpa pengguna pernah mengunjungi situs tracker itu. Firefox dan Safari mematikan tracking ini secara default; Chrome menonaktifkannya pada 2023.

GDPR (Regulasi Uni Eropa, Mei 2018): pengenal online (alamat IP, cookie) bila dikombinasikan dapat membuat profil & mengidentifikasi seseorang, sehingga cookie yang mengidentifikasi individu dianggap data pribadi. Pengguna memiliki kendali eksplisit apakah cookie diizinkan.

Web caches (proxy server)

  • Browser dikonfigurasi menunjuk ke cache lokal; semua request HTTP dikirim ke cache.
  • Jika objek ada di cache → cache mengembalikan objek (tanpa menyentuh origin server). Jika tidak → cache meminta ke origin server, menyimpan salinannya, lalu meneruskannya ke client.
  • Cache berperan ganda: server bagi client asal; client bagi origin server.

Mengapa caching? Mengurangi waktu respons (cache lebih dekat ke client), mengurangi traffic di access link institusi, dan memungkinkan "poor content providers" tetap efektif mengirim konten (like real estate: lokasi adalah segalanya).

Gambar 5 — Web cache melayani client dari salinan lokal, bukan dari origin server.

Contoh perhitungan caching

Skema: access link 1.54 Mbps; RTT router institusi → server = 2 detik; objek web = 100 Kbit; rata-rata request 15/detik → data rata-rata ke browser = 1.50 Mbps.

  • Tanpa cache: access link utilization = 1.5/1.54 ≈ 0.97 → antrian besar (delay menit). End-end delay ≈ 2 detik + menit + µs.
  • Opsi 1 — beli link lebih cepat (154 Mbps): utilization turun ke 0.0097, delay milidetik, tapi mahal.
  • Opsi 2 — pasang web cache dengan hit rate 0.4: hanya 60% request yang harus lewat access link → 0.6 × 1.5 = 0.9 Mbps → utilization 0.58; rata-rata end-end delay = 0.6×(2.01 s) + 0.4×(msec) ≈ 1.2 detik. Lebih murah dan lebih cepat dari beli link 154 Mbps.

Conditional GET (cache di sisi browser)

  • Tujuan: jangan kirim objek jika browser punya salinan cache yang sudah mutakhir.
  • Client menyebut tanggal salinan cache-nya di header request: If-modified-since: <date>.
  • Jika cache masih mutakhir, server membalas HTTP/1.0 304 Not Modified tanpa objek. Jika berubah, server membalas 200 OK beserta objek baru.

HTTP/2, HTTP/3, dan QUIC

VersiIde utama
HTTP 1.1HTTP persistent + pipelining beberapa GET pada satu koneksi TCP; server merespons berurutan (FCFS) → head-of-line (HOL) blocking: objek kecil bisa menunggu di belakang objek besar; retransmisi juga menghentikan pengiriman.
HTTP/2 [RFC 7540]Fleksibel: objek dikirim menurut prioritas yang diminta client, bisa push objek yang tidak diminta, dan objek dipecah jadi frame yang dijadwalkan interleave untuk meredakan HOL. Method, status code, header sebagian besar sama dengan HTTP/1.1.
HTTP/3Menambahkan keamanan dan error/congestion control per-objek di atas UDP via QUIC — karena HTTP/2 di atas satu koneksi TCP tetap cacat saat ada kehilangan paket (semua transmisi berhenti) dan tidak ada keamanan di TCP vanilla.
Gambar 6 — HTTP/2 memecah objek jadi frame dan menjadwalkannya (shortest job first → rata-rata delay menurun).

QUIC: Quick UDP Internet Connections

  • Protokol application layer di atas UDP untuk mempercepat HTTP — dipakai banyak server Google (Chrome, YouTube mobile).
  • Tumpukan HTTP/3: HTTP/2 (slimmed) → QUIC → UDP → IP (bukan HTTP/2 → TLS → TCP → IP).
  • Kontrol error & kongesti menyerupai TCP (relative terhadap algoritma TCP yang terkenal).

Connection establishment: TCP (reliability, congestion) + TLS (authentication, crypto) butuh dua handshake serial. QUIC menggabungkannya menjadi satu handshake 1 RTT. Bahkan dengan session ticket dari koneksi pertama (di-cache client), koneksi kedua bisa menjadi 0-RTT: client langsung mengirim data karena sudah punya kunci enkripsi.

Analogi: Web itu seperti toko swalayan HTTP stateless = kasir yang tidak mengingat Anda setiap kali antre — setiap transaksi berdiri sendiri. Cookies = kartu anggota yang pas Anda tunjukkan, kasir langsung tahu riwayat belanja Anda (dan toko lain yang melihat kartu Anda bisa melacak Anda juga). Web cache = etalase gigi di lingkungan Anda: barang yang sama diambil dari gudang dekat, bukan digores dari pusat distribusi di luar kota. HTTP/2 & HTTP/3 = kasir baru yang membuat pesanan Anda lebih dulu didahulukan dan memuat barang besar sekaligus kecil secara bersamaan, tidak menunggu satu gerobak besar selesai.

3 E-mail: SMTP dan IMAP

E-mail punya tiga komponen utama: user agents, mail servers, dan protokol pengirim SMTP.

Komponen e-mail

  • User Agent (a.k.a. "mail reader"): alat untuk menulis, menyunting, dan membaca e-mail — contoh: Outlook, aplikasi Mail di iPhone. Pesan keluar & masuk disimpan di server.
  • Mail server: punya user mailbox (pesan masuk untuk pengguna) dan message queue (pesan keluar yang menunggu dikirim).
  • SMTP bekerja antar mail server: server pengirim (acting as client) menghubungi server penerima (acting as server).
Gambar 7 — SMTP untuk kirim antar mail server; protokol akses (IMAP/HTTP) untuk mengambil e-mail dari server.

SMTP [RFC 5321]

  • Memakai TCP untuk mentransfer pesan secara andal dari client (mail server yang memulai koneksi) ke server, port 25.
  • Transfer langsung: server pengirim ke server penerima.
  • Tiga fase: (1) handshaking (sapaan/HELO), (2) transfer pesan, (3) closure.
  • Interaksi command/response ala HTTP: perintah berupa teks ASCII, jawaban berupa kode status + frase.
S: 220 hamburger.edu
C: HELO crepes.fr
S: 250 Hello crepes.fr, pleased to meet you
C: MAIL FROM: <alice@crepes.fr>
S: 250 alice@crepes.fr... Sender ok
C: RCPT TO: <bob@hamburger.edu>
S: 250 bob@hamburger.edu ... Recipient ok
C: DATA
S: 354 Enter mail, end with "." on a line by itself
C: Do you like ketchup?
C: How about pickles?
C: .
S: 250 Message accepted for delivery
C: QUIT
S: 221 hamburger.edu closing connection

Skenario: Alice mengirim e-mail ke Bob

  1. Alice memakai UA untuk menulis pesan "to" bob@someschool.edu.
  2. UA Alice mengirim pesan ke mail server-nya dengan SMTP; pesan masuk message queue.
  3. Sisi client SMTP di mail server Alice membuka koneksi TCP ke mail server Bob.
  4. Client SMTP mengirim pesan Alice lewat koneksi TCP.
  5. Mail server Bob menaruh pesan di mailbox Bob.
  6. Bob memanggil user agent-nya untuk membaca pesan.

Observasi tentang SMTP

  • SMTP memakai persistent connections.
  • SMTP menuntut pesan (header & body) dalam 7-bit ASCII.
  • Server SMTP memakai CRLF.CRLF untuk menentukan akhir pesan.
  • Bandingkan dengan HTTP: HTTP = client pull (client menarik konten), SMTP = client push (sender mendorong); keduanya interaksi command/response ASCII; HTTP membungkus tiap objek dalam satu message, SMTP mengirim banyak objek dalam multipart message.

Format pesan e-mail

SMTP (RFC 5321) mengatur pertukaran; RFC 2822 menentukan sintaks pesan e-mail itu sendiri (seperti HTML untuk halaman web). Pesan terdiri dari header, body, dipisah baris kosong. Header misalnya To:, From:, Subject: — beda dengan perintah SMTP MAIL FROM:/RCPT TO:! Body hanya karakter ASCII.

Protokol akses e-mail

  • SMTP menangani pengiriman/penyimpanan pesan ke server penerima; untuk mengambil dari server dibutuhkan mail access protocol: IMAP.
  • IMAP [RFC 3501]: pesan disimpan di server; IMAP menyediakan retrieval, deletion, dan folders pesan yang tersimpan di server.
  • HTTP: Gmail, Hotmail, Yahoo!Mail menyediakan antarmuka web di atas SMTP (kirim) dan IMAP/POP (ambil).
Analogi: Pos dan kotak surat SMTP = kurir yang membawa surat dari kantor pos Alice ke kantor pos Bob (MTA ke MTA). Mail server = kantor pos: kotak surat (mailbox) untuk surat masuk dan message queue untuk surat yang menunggu diantar. IMAP = Anda mengambil surat dari kotak di kantor pos dan bisa mengatur isinya dalam map-map — semua tetap tersimpan di server. Webmail (HTTP) = Anda membaca kotak surat lewat petugas yang membacakannya untuk Anda di kantor pos.

4 DNS: Domain Name System

Manusia mudah mengingat nama (cs.umass.edu), mesin mudah memproses angka (IP 32-bit). DNS menjembatani keduanya.

Masalah & solusi

  • Internet hosts & router diidentifikasi dengan IP address (untuk mengalamati datagram) dan "name" (dipakai manusia). Pertanyakannya: bagaimana memetakan antara keduanya?
  • DNS = distributed database yang diimplementasikan sebagai hierarki banyak name server + application-layer protocol: host & server DNS berkomunikasi untuk menerjemahkan nama. Catatan: ini fungsi inti Internet yang justru diimplementasikan sebagai protokol application layer — kompleksitas ada di tepi jaringan.
Mengapa tidak DNS terpusat? Jawabannya: tidak skalabel! Satu titik kegagalan, volume traffic raksasa, database jauh dari pemakai, dan sulit dirawat. Bandingkan: server DNS Comcast saja menangani 600 miliar query/hari; server DNS Akamai menangani 2,2 triliun query/hari.

Layanan DNS: (1) penerjemahan hostname → IP, (2) host aliasing (canonical & alias), (3) mail server aliasing, (4) load distribution (satu nama dipetakan ke banyak IP untuk web server replikasi).

Karakter DNS: database terdistribusi raksasa (~miliar record, tiap record sederhana), melayani triliunan query/hari dengan jauh lebih banyak read daripada write, performa kritikal (hampir setiap transaksi internet menyentuh DNS; perbedaan msec penting), terdesentralisasi secara organisasi & fisik, dan harus "bulletproof" (reliabel & aman).

Hierarki DNS

  • Root name servers: kontak terakhir (official, contact-of-last-resort) bagi name server yang tak bisa menyelesaikan nama; fungsi internet yang sangat penting dan dilindungi DNSSEC (autentikasi, integritas). Ada 13 root logical "server" di dunia; tiap "server" direplikasi berkali-kali. ICANN mengelola domain root.
  • TLD (Top-Level Domain) servers: bertanggung jawab atas .com, .org, .net, .edu, dan TLD negara seperti .cn, .uk, .fr, .ca, .jp. Contoh operator: Network Solutions (.com/.net), Educause (.edu).
  • Authoritative DNS servers: server DNS organisasi sendiri yang memberi pemetaan hostname→IP resmi untuk host bernamanya; bisa dikelola organisasi atau penyedia layanan.
  • Local DNS server: saat host melakukan query, ia dikirim ke local DNS server-nya; menjawab dari cache lokal (bisa kedaluwarsa!) atau meneruskan ke hierarki. Setiap ISP punya server ini (temukan via scutil --dns di macOS, ipconfig /all di Windows). Secara ketat ia bukan bagian dari hierarki.
Gambar 8 — Hierarki database DNS: root → TLD → authoritative. Client meminta www.amazon.com: query ke root → ke .com → ke amazon.com.

Iterated vs recursive query

Iterated query

Server yang dikontak membalas dengan nama server yang harus dikontak berikutnya: "Saya tidak tahu nama ini, tapi tanyakan pada server ini." Beban penyelesaian ada di client/local server. Sebuah local server yang mengirim 3 query ke hierarki (root→TLD→authoritative) demi satu nama memakai pola ini.

Recursive query

Beban penyelesaian diletakkan pada name server yang dikontak: ia yang meneruskan ke hierarki dan membalikkan jawaban final. Konsekuensi: beban berat di level atas hierarki.

Gambar 9 — Iterated query: local DNS di-bounce ke hierarki, membawa jawaban kembali ke host.

Caching DNS

  • Begitu sebuah name server mempelajari pemetaan, ia meng-cache-nya dan langsung membalas dari cache.
  • Memperbaiki waktu respons; entri cache kadaluwarsa setelah TTL.
  • TLD servers biasanya di-cache di local name servers.
  • Entri bisa kedaluwarsa/out-of-date: jika host berganti IP, perubahan mungkin tidak diketahui Internet-wide sampai semua TTL habis. Maka DNS adalah best-effort name-to-address translation!

DNS = database terdistribusi yang menyimpan resource records dalam format: (name, value, type, ttl).

Format pesan DNS

Query dan reply memakai format yang sama: header (identification 16-bit — reply memakai nomor yang sama dengan query, plus flags: query/reply, recursion desired/available, reply authoritative) diikuti bagian questions, answers, authority, dan additional info (masing-masing jumlah bervariasi).

Memasukkan nama Anda ke DNS

  1. Daftarkan nama (mis. networkutopia.com) ke registrar (mis. Network Solutions).
  2. Berikan nama & IP authoritative name server Anda (primary & secondary).
  3. Registrar menyisipkan RR NS dan A ke TLD server .com: (networkutopia.com, dns1.networkutopia.com, NS) dan (dns1.networkutopia.com, 212.212.212.1, A).
  4. Buat authoritative server lokal di IP tersebut: record A untuk www.networkutopia.com, record MX untuk domain.

Keamanan DNS

  • Serangan DDoS: bombardir root servers (sejauh ini gagal — ada traffic filtering, dan local DNS meng-cache IP TLD sehingga root bisa dilewati); bombardir TLD servers berpotensi lebih berbahaya.
  • Spoofing attacks: intercept query DNS dan membalas dengan jawaban palsu → DNS cache poisoning.
  • Pertahanan: DNSSEC [RFC 4033] — layanan autentikasi.
Analogi: DNS adalah buku telepon dunia Anda tidak menghafal nomor teman — Anda cari nama di buku telepon. Tapi satu buku raksasa di satu kota tak akan sanggup menampung semua orang dan satu antrean raksasa. Maka DNS seperti direktori telepon seluler yang saling dirujuk: tanya "informasi", diarahkan ke "kode area" (TLD), lalu ke "nomor rumah" (authoritative). Anda juga punya memori singkat (cache) — makin cepat, tapi ingatan itu bisa basi. DNSSEC = tanda tangan resmi di tiap halaman direktori agar nomor tidak diotak-atik penipu.

5 Video Streaming & CDN

Video streaming adalah konsumen terbesar bandwidth internet: Netflix, YouTube, Amazon Prime menanggung ~80% traffic ISP residensial (2020).

Konteks & tantangan

  • Skala: bagaimana menjangkau ~1 miliar pengguna?
  • Heterogenitas: pengguna punya kapabilitas berbeda (kabel vs seluler; bandwidth kaya vs terbatas).
  • Solusi: infrastruktur terdistribusi di application layer.

Video: dari gambar ke bit

  • Video = urutan gambar (mis. 24–30 gambar/detik). Gambar digital = larik piksel, tiap piksel diwakili bit.
  • Coding memakai redundansi untuk mengurangi bit:
    — Spatial coding (dalam satu gambar): alih-alih mengirim N nilai warna sama (semua ungu), kirim dua nilai: warna (ungu) + jumlah pengulangan (N).
    — Temporal coding (antar gambar): alih-alih mengirim gambar penuh di frame i+1, kirim selisihnya saja dari frame i.
  • CBR (constant bit rate): laju encoding tetap. VBR (variable bit rate): laju berubah-ubah sesuai seberapa banyak coding spasial/temporal diterapkan.
  • Contoh: MPEG 1 (CD-ROM) 1.5 Mbps; MPEG 2 (DVD) 3–6 Mbps; MPEG 4 (umum di internet) 64 Kbps–12 Mbps.

Streaming stored video

Video direkam lalu disimpan. Saat streaming, client memutar bagian awal video sementara server masih mengirim bagian akhir. Tantangan utama:

  • Continuous playout constraint: selama pemutaran, timing pemutaran harus cocok dengan timing asli — tetapi delay jaringan bervariasi (jitter) → butuh buffer di sisi client.
  • Interaktivitas client: pause, fast-forward, rewind, loncat.
  • Paket video dapat hilang dan perlu di-retransmisi.
Gambar 10 — Buffer client menyerap variasi delay (jitter) agar pemutaran tetap mulus. Pada saat t₀, 6 chunk sudah tiba dan 2 sudah diputar → 4 chunk di buffer.

DASH: Dynamic Adaptive Streaming over HTTP

Peran server

  • Membagi file video jadi banyak chunk.
  • Tiap chunk di-encode pada banyak laju berbeda; tiap laju disimpan di file berbeda.
  • File direplikasi di berbagai node CDN.
  • Berkas manifest menyediakan URL untuk chunk-chunk berbeda.

Peran client ("intelligence" di client)

  • Secara periodik memperkirakan bandwidth server→client.
  • Konsultasi manifest; meminta satu chunk per saat dengan memilih laju encoding maksimum yang bisa ditopang bandwidth sekarang.
  • Bisa mengubah laju dari waktu ke waktu, dan mengambil dari server yang berbeda.

Client yang menentukan: kapan meminta chunk (agar buffer tidak kelaparan/overload), laju apa (kualitas naik saat bandwidth banyak), dan dari URL mana (server yang dekat / bandwidth tinggi).
Ringkasan: Streaming video = encoding + DASH + playout buffering.

Content Distribution Networks (CDN)

Tantangan: bagaimana menjalankan konten dari jutaan video menuju ratusan ribu pengguna bersamaan? Opsi 1 — mega-server tunggal: satu titik kegagalan, titik kemacetan jaringan, jalur panjang ke client jauh → tidak skalabel.

Opsi 2 — simpan/sajikan salinan video di banyak situs terdistribusi (CDN):

Enter deep

Dorong server CDN jauh masuk ke banyak access network, dekat pengguna. Contoh: Akamai ±240.000 server di >120 negara (2015).

Bring home

Jumlah lebih kecil (puluhan) cluster besar di POPs dekat access network. Contoh: dipakai Limelight.

Gambar 11 — Konten direplikasi ke banyak node CDN di berbagai lokasi; client mengambil dari node terdekat.

Studi kasus: Netflix (OTT)

  1. Bob mengelola akun Netflix (server registrasi/akuntansi Netflix di Amazon cloud).
  2. Bob menjelajah video Netflix; berkas manifest untuk video tertentu dikembalikan.
  3. Pemilihan server DASH dikontak; streaming dimulai.
  4. Netflix menyimpan salinan konten di node OpenConnect CDN di seluruh dunia; manifest menunjuk salinan; client mengambil pada laju tertinggi yang didukung, dan bisa pindah laju/salinan jika jalur padat.

OTT = "over-the-top": host-to-host communication as a service yang mengatasi Internet padat dari "tepi". Tantangan OTT: konten apa ditaruh di node CDN mana? Dari node mana mengambil, pada laju berapa?

6 Socket Programming (UDP & TCP)

Tujuan: belajar membangun aplikasi client/server yang berkomunikasi memakai soket — "pintu" antara proses aplikasi dan protokol transport end-to-end.

Ada dua tipe soket untuk dua layanan transport: UDP (unreliable datagram) dan TCP (reliable byte-stream). Aplikasi contoh sepanjang bagian ini: client membaca baris teks dari keyboard, mengirim ke server; server mengubahnya menjadi huruf kapital dan mengembalikannya; client menampilkannya.

UDP: tanpa koneksi

  • Tanpa "connection"; tidak ada handshaking sebelum mengirim.
  • Sender secara eksplisit menempelkan IP tujuan + nomor port ke tiap paket.
  • Receiver mengekstrak IP asal + port dari paket yang diterima.
  • Data bisa hilang atau tidak berurutan.
  • Dari kacamata aplikasi: transfer unreliable dari kelompok bytes ("datagram").

TCP: berorientasi koneksi

  • Client harus menghubungi server dulu: server harus berjalan dan membuat welcoming socket.
  • Client membuat soket TCP dengan menentukan IP + port server; koneksi TCP dibangun.
  • Saat dikontak client, TCP server membuat soket (connectionSocket) baru untuk proses server tsb berkomunikasi dengan client itu → server bisa berbicara dengan banyak client sekaligus (dibedakan lewat source port & IP client).
  • TCP menyediakan reliable, in-order byte-stream ("pipa") antar proses.

Client UDP (Python)

# UDPClient.py
from socket import *
serverName = 'hostname'
serverPort = 12000
clientSocket = socket(AF_INET, SOCK_DGRAM)   # buat UDP socket
message = input('Input lowercase sentence:')
clientSocket.sendto(message.encode(), (serverName, serverPort))
                       # tempel nama+port server, kirim ke soket
modifiedMessage, serverAddress = clientSocket.recvfrom(2048)
                       # baca data bytes dari soket
print(modifiedMessage.decode())
clientSocket.close()

Server UDP (Python)

# UDPServer.py
from socket import *
serverPort = 12000
serverSocket = socket(AF_INET, SOCK_DGRAM)   # buat UDP socket
serverSocket.bind(('', serverPort))          # ikat ke port 12000
print('The server is ready to receive')
while True:
    message, clientAddress = serverSocket.recvfrom(2048)
                            # baca dr soket: pesan + alamat client (IP & port)
    modifiedMessage = message.decode().upper()
    serverSocket.sendto(modifiedMessage.encode(), clientAddress)
                            # kirim balik kapital ke client tsb

Client TCP (Python)

# TCPClient.py
from socket import *
serverName = 'servername'
serverPort = 12000
clientSocket = socket(AF_INET, SOCK_STREAM)  # buat TCP socket
clientSocket.connect((serverName, serverPort)) # sambung ke server
sentence = input('Input lowercase sentence:')
clientSocket.send(sentence.encode())
modifiedSentence = clientSocket.recv(1024)
print('From Server:', modifiedSentence.decode())
clientSocket.close()
# Perhatikan: tidak ada lagi "attach server name, port" per paket.

Server TCP (Python)

# TCPServer.py
from socket import *
serverPort = 12000
serverSocket = socket(AF_INET, SOCK_STREAM)  # welcoming socket
serverSocket.bind(('', serverPort))
serverSocket.listen(1)                       # mulai mendengar
print('The server is ready to receive')
while True:
    connectionSocket, addr = serverSocket.accept()
                            # tunggu; dibuat soket baru utk client ini
    sentence = connectionSocket.recv(1024).decode()
    capitalizedSentence = sentence.upper()
    connectionSocket.send(capitalizedSentence.encode())
    connectionSocket.close()                 # tutup koneksi client ini saja
# tanpa alamat (tidak seperti UDP); welcoming socket tetap terbuka
Gambar 12 — Interaksi soket TCP: setup koneksi dulu, lalu pertukaran request/reply, soket per-client dibuat oleh accept().

Socket timeouts (kasus "anak gembala")

Kadang program harus menunggu salah satu dari beberapa kejadian: balasan dari ujung soket lainnya, atau timeout (timer); atau menunggu balasan dari beberapa soket sekaligus (select(), multithreading). Timeout dipakai luas di jaringan. Di soket Python: settimeout() menyalakan timer; jika tak ada pesan sebelum batas, operasi recv() dipotong dan melempar exception timeout yang harus ditangani dengan blok try/except.

# Toy example: server TCP "para penduduk desa"
from socket import *
serverPort = 12000
serverSocket = socket(AF_INET, SOCK_STREAM)
serverSocket.bind(('', serverPort))
serverSocket.listen(1)
counter = 0
while counter < 3:
    connectionSocket, addr = serverSocket.accept()
    connectionSocket.settimeout(10)          # timeout 10 detik
    try:
        wolf_location = connectionSocket.recv(1024).decode()
        send_hunter(wolf_location)           # fungsi penduduk desa
        connectionSocket.send('hunter sent')
    except timeout:                          # tangkap exception timeout
        counter += 1
    connectionSocket.close()
  • Ceritanya: anak gembala suka menyambung ke server tanpa mengirim lokasi serigala. Penduduk desa berhenti mendengarkan setelah 3 kali timeout (10 detik) berturut-turut.
  • settimeout(None) menghapus timeout; settimeout(0) membuat soket non-blocking.
Analogi: UDP vs TCP adalah telepon UDP = pos kilat tanpa resi: tulis alamat di tiap surat, lempar, semoga sampai, boleh hilang. TCP = telepon: kamu harus "menyambung dulu" (bel), baru bicara; operator membuat "saluran" khusus untuk tiap pembicara; urutan kata selalu benar. Timeout + try/except = menunggu jawaban di interkom: kalau 10 detik tak ada jawaban, buzzer berbunyi (exception) dan Anda mengurus hal lain, alih-alih diam selamanya menatap pengeras suara.

7 Rangkuman

Yang dipelajari di bab ini — plus tema penting yang diulang sepanjang materi.

Arsitektur aplikasi

  • Client–server: server always-on, IP permanen; client tidak langsung berkomunikasi satu sama lain.
  • P2P: tanpa server sentral, self-scaling, kompleks di manajemen.

Kebutuhan service aplikasi

  • Reliability (keutuhan data).
  • Bandwidth / throughput.
  • Delay / timing.
  • Keamanan.

Model layanan transport Internet

  • TCP: connection-oriented, reliable.
  • UDP: unreliable, datagrams.

Protokol spesifik

  • HTTP, SMTP/IMAP, DNS.
  • P2P: BitTorrent.
  • Video streaming & CDN, DASH.
  • Socket programming TCP & UDP.

Yang paling penting: belajar tentang protokol!

client/server request-reply centralized vs decentralized stateless vs stateful scalability reliable vs unreliable transfer "complexity at network edge"

Soal 14 · Isian protokol (10 pts)
Alice menggunakan Gmail via browser dan Bob membaca suratnya dengan mail client yang menyimpan pesan di mail server perusahaannya. Saat Alice mengirim pesan ke Bob: browser-nya mendorong ke server Gmail memakai protokol ____; server Gmail menyerahkannya ke mail server Bob memakai protokol ____; dan mail client Bob mengambilnya dari mail server memakai protokol ____. (Tulis akronim protokol, huruf kapital, tanpa versi.)
Kunci: HTTP ; SMTP ; IMAP
Webmail: HTTP/HTTPS dari browser ke Gmail; antar mail server: SMTP; mail client mengambil: IMAP (bukan POP, karena disebut "menyimpan pesan di server").
Soal 15 · Pilihan ganda (5 pts)
Host mengklik link yang URL-nya belum ter-cache, sehingga dibutuhkan DNS lookup. Tiga server DNS dikunjungi sebelum IP kembali, masing-masing dengan RTT 20 ms. Halaman hanya file HTML kecil (waktu transmisi = 0) dan RTT host–web server = 30 ms. Memakai non-persistent HTTP, berapa waktu dari klik sampai objek diterima?
A. 120 ms
B. 180 ms
C. 60 ms
D. 150 ms
E. 90 ms
Kunci: A. 120 ms
DNS: 3 × 20 = 60 ms; TCP (1 RTT = 30 ms) + request/response (1 RTT = 30 ms). Total 60 + 30 + 30 = 120 ms.
